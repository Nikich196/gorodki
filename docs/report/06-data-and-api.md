# 6. Данные и API

Глава описывает, где хранятся данные игры, как сервер и телефон договариваются о форме запросов и как телефон
доставляет забег без сети. Состояние — на 24.09.2026; несделанное помечено «план». Подробности — в `docs/architecture/`
(`data-model.md`, `runs.md`, `sync.md`, `realtime.md`, `ios-app.md`) и в ADR 0004.

## 6.1. Модель данных сервера

База — PostgreSQL 17 + PostGIS 3.3 на Supabase Free; сервер работает с ней через EF Core и Npgsql, пул — 8 соединений.
Таблицы — в схеме `app`, расширения PostGIS и `btree_gist` — в схеме `extensions`. Правил игры в базе нет (ADR 0003).

**16 таблиц данных** — посчитано по свойствам `DbSet` в `AppDbContext.cs` и по вызовам `CreateTable` в миграциях, оба
раза 16 (служебная таблица истории миграций `ef_migrations_history` не в счёт).

| Назначение | Таблицы | Главные столбцы и правила |
|---|---|---|
| Игроки и вход | `users`, `invites`, `refresh_tokens` | Ник уникален без учёта регистра; цвет 0–11; роль (игрок, демо, админ); подтверждение 16+, версия согласия, согласие на показ профиля; отметки удаления и заморозки. Инвайт — `used_count ≤ max_uses`. От refresh-токена хранится только SHA-256 и «семья» входа |
| Правила и календарь | `game_configs`, `seasons` | Номер версии конфига и все числа правил в `jsonb`. Три сезона (С0–С2) заложены в модель; начало — полночь по Минску, в UTC |
| Забеги | `runs`, `run_chunks` | Лига, источник, версия конфига, статус, до какой точки обработан, сдвиг часов, установка, счётчики кусков и байт; **один активный забег на игрока** — уникальный индекс. Кусок: ключ «забег + номер первой точки», точки в двоичном виде (21 байт на точку), SHA-256 содержимого; **куски не пересекаются по номерам** — ограничение `EXCLUDE` |
| Захваты и откат | `captures`, `capture_journal`, `capture_journal_pieces`, `capture_rollbacks`, `contested_zones` | Заявка: UUIDv5, номер в забеге, первая и последняя точка петли, статус 0–4, аренда обработчика, порядок применения (последовательность `capture_apply_seq`), контур. Журнал: след захвата по тайлу и земля «до» и «после». Откат: кто, кого, почему, итог. Зоны «спорная» большой петли: чужая земля внутри по тайлу и срок (24 ч) — отдельный слой, куски не меняет |
| Карта | `parcels`, `tile_versions` | Кусок земли: лига, тайл, владелец, уровень 1–3, щит, осада, окно снятия уровней, многоугольник. Версия тайла растёт при каждом изменении земли в нём |
| «Исследование» | `fog_tiles`, `leaderboard_snapshots` | Туман по тайлам уровня 14: биты 256 × 256, сжатые Deflate, число открытых клеток 1–65 536, версия. Срез рейтинга: сутки, слой, сезон, игрок → значение и место |
| Приватность | `privacy_zones` | Центр круга (широта, долгота); радиус 400 м — общий, из игрового конфига |

**Геометрия.** Кусок земли — `geometry(Polygon, 32634)`: UTM 34N, вершины на сетке 0,1 м, один простой многоугольник
в одном тайле 1 × 1 км. База сама отвергает неправильную геометрию (`st_isvalid`), даже если ошибся движок; по месту
ищет GiST-индекс. Журнал хранит геометрию в TWKB на той же сетке. Считает сервер (NetTopologySuite), PostGIS хранит.

**Миграции.** 14 миграций EF Core, от `InitialSchema` до `LeaderboardSnapshots` (посчитаны файлы папки `Migrations`
без `*.Designer.cs` и снимка модели); на Render применяются при старте сервера. Правка модели без миграции роняет
`MigrationsTests`, функция PostGIS 3.4+, которой нет на Supabase, — `PostgisCompatibilityTests`.

**Хранение и бюджет.** Бесплатная база — 500 МБ; переполненная, она становится только для чтения, и встаёт вся игра.
Поэтому сырые точки хранятся 14 дней (`RunRetention`: содержимое кусков стирается, номера и отпечаток остаются), журнал
захватов и срезы рейтинга — 7 дней; чистки идут раз в час. С 350 МБ `GET /health/ready` отвечает 503
(`StorageHealthCheck`), и пингер присылает письмо. План: устройства, кланы, лента, фишки, тайники — новыми миграциями.

## 6.2. API: REST и один контракт

**Контракт — источник истины.** Телефон и сервер общаются по REST с JSON. Описание OpenAPI 3.1 сервер (ASP.NET Core 10)
строит сам; тест `OpenApiContractTests` сравнивает его с `contracts/openapi.v1.json`, а файл — с копией в Swift-пакете
`GorodkiAPI`: поменяли адрес или поле и не обновили контракт — тест падает. Обновить файл можно только явной командой,
и правка видна в pull request. Всё закрыто по умолчанию (без access-токена — 401); вход и проверки здоровья открыты явно.

**Состав:** 22 операции на 20 путях, 9 групп, 61 схема данных (посчитано скриптом по разделам `paths`
и `components.schemas` контракта; группы — его теги). Вне контракта: два адреса администратора `/admin/…`,
`/health/ready` для пингера и хаб `/hubs/game` (раздел 6.4).

| Группа | Операций | Адреса |
|---|---|---|
| Вход | 3 | `POST /auth/google`, `POST /auth/refresh`, `POST /auth/logout` |
| Профиль | 6 | `GET /me`, `DELETE /me`, `GET /me/export`, `GET` и `POST /me/privacy-zones`, `DELETE /me/privacy-zones/{id}` |
| Забеги | 4 | `POST /runs`, `PUT /runs/{runId}/chunks/{firstSeq}`, `POST /runs/{runId}/finish`, `GET /runs/{runId}` |
| Захваты | 2 | `POST /runs/{runId}/loops`, `GET /runs/{runId}/captures` |
| Исследование | 4 | `GET /fog`, `DELETE /fog`, `GET /fog/summary`, `GET /leaderboards/exploration` |
| Карта, Конфиг, Сезоны, Служебное | по 1 | `GET /territory`, `GET /config`, `GET /seasons`, `GET /health` |

**Форма данных и ошибки.** Время — целые миллисекунды Unix по часам телефона; сдвиг часов сервер считает сам по полю
`sentAtMs`. Числа — только числами, перечисления — только строками. Ошибки — ProblemDetails (RFC 9457) с полем `code`,
стабильным кодом для приложения (`run_not_found`, `chunk_conflict`, `daily_run_limit`…): приложение ветвится по коду,
а не по тексту. Дополнительные поля: `problems` — что не так с куском (без координат), `overlaps` — занятые номера точек.

**Идемпотентность: любой запрос можно повторить.** Забег: идентификатор создаёт телефон, повтор `POST /runs` — 200 без
изменений. Кусок: адрес — «забег + номер первой точки», повтор узнаётся по SHA-256 содержимого (200, `duplicate: true`),
другие точки на занятых номерах — 409 `chunk_conflict` с `overlaps`. Заявка петли: идентификатор — UUIDv5 от забега
и номера последней точки; новая — 202, повтор — 200 с текущим итогом. Повтор завершения ничего не меняет.

**Лимиты** (`RunLimits`, `Program.cs`): в куске — до 1 200 точек и 1 200 записей датчиков каждого вида, запрос
с куском — до 1 МБ; на забег — 400 кусков и 1 МБ; на игрока в сутки — 10 забегов и 5 МБ; куски принимаются 7 дней;
часы телефона сбиты не больше чем на 12 часов. Частота на игрока: адреса забегов и заявок — 60 запросов в минуту
(запас 120), адреса чтения (карта, туман, итоги заявок…) — 120 (запас 240).

**Клиент для iOS генерируется** (ADR 0004) плагином swift-openapi-generator при сборке пакета `GorodkiAPI`, ручной
клиент не понадобился. 16 образцов ответов `contracts/samples` пишет сам сервер (`ApiSamplesTests`), 11 Swift-тестов
пакета разбирают каждый образец и гоняют клиент на подставном транспорте.

## 6.3. Офлайн-синхронизация на телефоне

Главное правило телефона — **никогда не ждать сервер**: забег пишется в очередь и уходит, когда есть сеть. Очередь
хранит пакет `GorodkiPersistence`: GRDB 7, SQLite в режиме WAL, файл `Application Support/gorodki.sqlite`, три таблицы —
`syncRun`, `syncChunk`, `syncClaim` (ключи — столбцами, запись — JSON модели), схема — миграциями. Каждая операция —
одна транзакция; забег меняется только атомарным `updateRun`, поэтому запись и синхронизация, работающие одновременно,
не затирают поля друг друга. Очередь — не история: подтверждённые сервером куски стираются.

**Запись** (`RunRecorder`, пакет `GorodkiSync`). Кусок запечатывается раз в минуту, по 120 точек, при 1 200 записях
датчиков одного вида или сразу при петле; после этого его границы не меняются. Точку от GPS до очереди ведёт
`RunSession`: номер, округление, судья, запись всех точек, детектор петли и заявка. Идущий забег ведёт `RunTracker`:
точки CoreLocation, датчики CoreMotion и таймер — одной очередью, строго по порядку; после выгрузки приложения забег
продолжается по базе, а не по флагу. Экрана забега ещё нет (этап 2), на телефоне трекер не проверен — запись и доставку
проверяют тесты на Linux с подменными источниками и поддельным сервером.

**Проход** (`SyncEngine.syncOnce()`): один за раз, только забеги вошедшего игрока, от раннего к позднему. Порядок:
`POST /runs` → куски по порядку, после каждого — заявки петель, чьи точки уже у сервера → `POST …/finish` →
`GET /runs/{id}`: пустой `missing` — куски стираются, иначе снова в очередь (не больше трёх кругов) → итоги заявок
(`GET …/captures`). Состояние после каждого ответа уже в базе, поэтому проход можно оборвать где угодно. На 409
`chunk_conflict` кусок режется: уходят только номера, которых нет в `overlaps`; на 404 `run_not_found` забег начинается
заново; окончательные отказы (`run_invalid`, `claim_conflict`…) не повторяются.

**Когда повторять.** Проход останавливается без сети, на 5xx, 401, 429 без кода лимита, при сбитых часах и удалении
аккаунта. Следующий назначает чистая функция `SyncBackoff.next`: нет сети или 5xx — через 15 с, 30 с, 1 мин… вдвое,
до 15 минут; 429 — не раньше чем через минуту; 401 — только после входа; сбитые часы и удаление аккаунта — после
действия игрока; досылка — через 15 с; отложенный забег или исчерпанный суточный объём — через час; заявки без итога
при открытом приложении — опрос раз в 30 с. Проход запускают и события (`SyncScheduler`): выход на передний план,
возврат сети, вход (эти три сбрасывают шаг повторов), новое в очереди, подсказка реального времени.

**В фоне** (BGTasks). Уходя в фон, приложение просит у iOS около 30 секунд на проход. По его итогу оно заказывает
пробуждения (`BackgroundSyncPlan`): при недоставленных забегах — `BGAppRefreshTask` и `BGProcessingTask` с сетью, при
одних заявках — только первое; не раньше чем через 15 минут, а когда именно — решает iOS. Правило проверено тестами;
как часто iOS будит на деле, покажет только телефон (план: пробная прогулка).

**Вход и обновление токена.** Access-токен живёт 15 минут, refresh-токен — 30 дней и меняется при каждом обновлении;
повтор заменённого refresh-токена позже 60 секунд сервер считает кражей. `AuthMiddleware` подписывает запросы, и на 401
все одновременные запросы ждут **одного** `POST /auth/refresh` (`TokenStore.renew`), а потом повторяются один раз (тест:
20 одновременных 401 — ровно одно обновление). Отказ в обновлении — выход, сбой сети — вход сохраняется. Токены лежат
в Keychain «после первой разблокировки, только это устройство». Логика входа и регистрации (`SignInService`: инвайт, 16+, согласие, коды ответов) готова; экран и Google Sign-In —
план (ждут Client ID).

## 6.4. Реальное время

SignalR-хаб `/hubs/game` (только с входом) раздаёт **только подсказки**: `TilesChanged` (лига, тайлы) и `CaptureDecided`
(забег, заявка, итог); данные — всегда через REST. Приложение после каждого подключения шлёт `Subscribe` с лигой. Чужое
изменение приходит не раньше границы публичности — «сейчас − 20 минут», шагами по 5 минут (глава 7). Сервер шлёт
подсказку только после фиксации транзакции, склеивает подсказки за секунду, держит не больше трёх соединений на игрока.

Приложение держит одно соединение, пока оно на переднем плане, и переподключается без конца: сразу, если соединение
прожило 30 секунд, иначе через 1, 2, 4, 8, 16, 30 секунд и дальше по 30 (стандартная политика SignalR — 0, 2, 10, 30 с
и сдаться — короче холодного старта Render Free). Токену при подключении должно оставаться жить не меньше минуты.
На подключение и на `CaptureDecided` запускается проход синхронизации; `TilesChanged` обработает карта (план, этап 2).
Потеря подсказки ничего не ломает: при подключении приложение пересинхронизируется, заявки страхует опрос раз в 30 с.
Проверено интеграционными тестами и пробой настоящего Swift-клиента против настоящего хаба (24.09, не в CI);
WebSocket на iPhone ещё не проверен. Подробно — `docs/architecture/realtime.md` и `ios-app.md`.
