# 10. Развёртывание и эксплуатация за $0

Состояние — на 24.09.2026. **Сервер ещё не развёрнут**: описание сервиса (`render.yaml`) и руководство
(`docs/guides/deploy-render.md`) готовы, база на Supabase создана, все 14 миграций применены; сам деплой делает
Никита — аккаунт Render на нём. Всё, что ещё не сделано, помечено «план».

## 10.1. Где всё живёт и сколько стоит

Бюджет на сервер — строго $0 (PLAN.md, §1); платное — только с согласия Никиты (§9, «план Б»). Fly.io, Cloudflare
и Backblaze не берём — заблокированы в РБ (D7).

- **Render Free — сервер** (`render.yaml`: Docker, регион Франкфурт, рядом с базой). Ограничения (§9, D7): 0,1 CPU,
  512 МБ; 750 часов в месяц на всё рабочее пространство, а один сервис без сна тратит около 720 — второй заводить
  нельзя; сон после 15 минут без запросов; возможны перезапуски и приостановка. Что делаем: один сервис, пингер
  (10.3), Hangfire — только для задач по расписанию, с одним исполнителем (ADR 0005: +6–11 МБ), нагрузочные прогоны —
  только локально (§9).
  Под квотой 10 % CPU локально p95 захвата — 1,10–1,39 с при пороге 2 с, без времени базы (ADR 0003); на настоящем
  Render скорость и холодный старт ещё не мерили (спайк S9).
- **Supabase Free — база**: PostgreSQL 17 + PostGIS 3.3.7, проект `gorodki` во Франкфурте (eu-central-1), Data API
  выключен — в базу ходит только сервер (журнал, 23.09). Ограничения: 500 МБ, при переполнении база только для
  чтения — встанет вся игра; пауза после недели простоя (§9). Что делаем: сроки хранения и бюджет в `/health/ready`
  (10.3), пингер с настоящим запросом к базе, пул соединений сервера — 8 (`AppDbContext.MaxPoolSize`), тесты на
  образе с той же PostGIS (глава 9). Туман по оценке плана — 10–30 МБ на 200 игроков (§7.3).
- **GitHub**: публичный репозиторий, CI на GitHub Actions (10.2), IPA — в артефактах запусков. Раннер `xcode-27` —
  preview, поэтому раз в неделю резервная сборка на `macos-26` (D8); приложение собирается, только если менялся
  iOS-код (`ios.yml`). GitHub Pages (сайт, веб-компаньон, `/live`) — план (D7).
- **Apple**: пока бесплатный Apple ID и Sideloadly (D9, `install-on-iphone.md`). Подпись живёт 7 дней; 10 App ID
  за 7 дней на аккаунт, «Городки» занимают 2. Что делаем: отдельный «расходный» Apple ID, автообновление подписи,
  переустановка за 1–2 дня до показа; запасные установщики — AltServer + AltStore Classic или Impactor. Платный
  аккаунт Никиты (от другого проекта) для «Городков» — решение к 20.10 (§1, §14): подпись на год и TestFlight; без
  него на телефонах играют 5–15 человек, остальным — веб-компаньон (D9).
- **cron-job.org** (запасной — UptimeRobot) — пингер; **Sentry** (регион EU) — ошибки приложения, без персональных
  данных (§7.2). Оба аккаунта — на Егоре (#39, #38); в журнале они пока среди следующих шагов.

## 10.2. Путь изменения: от ветки до сервера и телефона

1. **Ветка → pull request** по шаблону: что сделано, зачем, как проверено, нет ли секретов (`CONTRIBUTING.md`).
2. **Обязательные проверки.** `main` защищена: только через PR и только после трёх проверок, одобрения не нужны (§8);
   PR сливается squash — одним коммитом. На администратора репозитория защита не распространяется (`enforce_admins`
   выключен). Три проверки:
   - `backend` (Ubuntu): сборка Release, где любое предупреждение — ошибка (`Directory.Build.props`); все тесты,
     включая интеграционные на образе Supabase; оформление кода (`dotnet format --verify-no-changes`); сборка
     Docker-образа для Render;
   - `ios-core` (контейнер `swift:6.4-noble`): тесты пяти Swift-пакетов и `swift format lint --strict`;
   - `ios-build` (раннер `xcode-27`): XcodeGen, Debug-Free для симулятора, Release-Free и Release-Paid для iPhone
     без подписи; дымовой запуск на симуляторе (передний план и фон — без падения) и тесты приложения `GorodkiTests`
     (их число сверяется по пакету результатов: «TEST SUCCEEDED» бывает и при нуле тестов). Если `ios/` не менялась,
     проверка пропускается, и GitHub считает её пройденной. Если же упала сама задача-фильтр `changes`, приложение
     собирается всё равно: иначе сбой фильтра молча пропустил бы непроверенный iOS-код. Первый шаг — версии внешних
     Swift-пакетов: в `ios/project.yml` они закреплены точно по `Package.resolved` пакетов (`check-spm-pins.py`),
     чтобы приложение собиралось с теми же версиями, что проверили тесты пакетов.

   Новый коммит в PR отменяет прогон прежнего; прогоны `main` не отменяются никогда: Render выкатывает сервер, только
   если все проверки коммита зелёные, а отменённая проверка зелёной не бывает. Сбой симулятора на preview-раннере
   поэтому держит и слияние, и деплой — лечится повтором, а не `continue-on-error`.
3. **Необязательные запуски**: `ios-build-xcode26` — по понедельникам в 06:00 по Минску; `ipa` — после изменений
   iOS-кода в `main`: два IPA для Sideloadly (без подписи и с ad-hoc подписью), хранятся 14 дней; Dependabot — раз
   в месяц по одному сводному обновлению для NuGet и для GitHub Actions, без мажорных версий.
   Необязательные проверки слияние не держат; сливать можно, когда зелёные три обязательные
   (`gh pr checks <PR> --required`):
   - `ios-snapshots` — в PR с изменениями `ios/` и кнопкой: UI-тесты на симуляторе снимают экраны, которые
     открываются без сервера, PNG — в артефакте запуска на 14 дней (приложение видно без Mac); имена SF Symbols
     из кода проверяются на `macos-26` (план относит эту проверку к автоматическим, почему она не обязательная —
     [отступления от плана](../plan-deviations.md), п. 7). На `main` задачи пропускаются и кнопкой: упавшая
     проверка коммита `main` могла бы отменить деплой;
   - `geo-nightly` — каждую ночь около 03:23 по Минску (GitHub запускает по расписанию с задержкой) тесты геодвижка
     на 10 000 новых случайных историях (глава 9). Проверка ночного прогона привязана к последнему коммиту `main`,
     а Render ждёт все проверки коммита: начнись ночной прогон, пока идут проверки свежего слияния в сервер, его
     красный цвет молча отменил бы деплой. Поэтому шаг перед тестами читает проверки коммита (GitHub API) и пропускает
     тесты, если коммиту меньше 10 минут или какая-то его проверка ещё идёт либо закончилась меньше 10 минут назад;
     пропуск проверку не красит.
4. **Развёртывание** (настроено, ещё не запускалось). Render выкатывает `main`, только если изменилась `backend/**`
   и все проверки GitHub зелёные (`autoDeployTrigger: checksPass`); это заменяет deploy hook из плана (§8) и не
   требует секрета в GitHub. Образ из `backend/Dockerfile`: сборка на .NET SDK 10.0, запуск на
   `aspnet:10.0-noble-chiseled-extra` — без shell и пакетного менеджера, но с tzdata и ICU для времени Минска.
   При старте сервер применяет миграции (`Database__MigrateOnStartup=true` → `MigrateAsync()` в `Program.cs`).
   Два экземпляра во время деплоя друг другу не мешают: заявки берутся в аренду (ADR 0005).

## 10.3. Эксплуатация

| Адрес | Кто вызывает | Что проверяет | Ответ |
|---|---|---|---|
| `/health` | Render | Жив ли процесс; в базу не ходит | 200: версия, коммит, время Минска, игровой день |
| `/health/ready` | Пингер | `database` — база отвечает; `storage` — меньше ли 350 МБ | 200 `healthy` или 503: статусы проверок; числа и описания — только администратору |

503 значит: база недоступна или заполнена на 350 МБ и больше (предел — 500 МБ, `StorageHealthCheck`). Пингеру и
игрокам в теле — только статусы: общий и у проверок `database` и `storage`. Размер базы, соединения, куски земли,
вершины и описания проверок видит только администратор (токен с ролью `admin`): в описании упавшей проверки — текст
ошибки базы с адресом пула и именем пользователя. Render смотрит только на `/health`, поэтому из-за 503 сервер не
перезапускается. Пустая база с PostGIS — около 19 МБ (замер 23.09).

**Сроки хранения** — чистки фонового обработчика раз в час:

| Что | Сколько живёт | Код |
|---|---|---|
| Сырые точки забега (номера точек и время остаются) | 14 дней | `RunRetention` |
| Журнал захватов (для отката) | 7 дней | `CaptureProcessor` |
| Срезы рейтингов | 7 дней | `LeaderboardSnapshots` |
| Незавершённый забег | закрывается через сутки после предела длины (4 ч) | `RunRetention` |
| Аккаунт, удаление которого запрошено | ближайший проход, не раньше 20 мин (закон — до 15 дней) | `AccountDeletion` |

**Фоновый обработчик** (`CaptureWorker`) — один поток: каждые 5 секунд или по сигналу — захваты, визиты, туман,
раскрытия, откаты; раз в час — чистки и срез рейтингов. Время последней чистки хранится в памяти процесса, поэтому
после перезапуска чистки идут первым же проходом. Задачи по расписанию — Hangfire (ADR 0005, гибрид: очередь своя,
расписание — Hangfire, [PLAN §7.3](../PLAN.md#73-бэкенд)): пока в нём стирание истёкших токенов входа, ещё три часовые
чистки переносит E6 ([jobs.md](../architecture/jobs.md)); журнал захватов и удаление аккаунтов остаются в обработчике.

**Пингер** (план, #39): `GET /health/ready` каждые 10 минут — чаще, чем Render засыпает, а запрос к базе не даёт
Supabase уйти на паузу. На 503 он пришлёт письмо.

**Лимиты запросов** сейчас — на игрока (`Program.cs`): забеги и заявки — 60 в минуту (запас 120), чтение — 120
(запас 240), сверх — 429. Лимиты по IP для входа — после деплоя (#52): сначала надо увидеть, в каком заголовке
Render передаёт адрес телефона.

**Секреты** — только в GitHub Secrets и переменных Render, в публичном репозитории их нет (`CONTRIBUTING.md`).
Строку подключения Render спрашивает при создании сервиса, ключ подписи токенов генерирует сам (256 бит); без ключа
сервер не стартует. Workflows секретов не используют. Передача — одноразовой ссылкой (§9); секрет попал в коммит —
ключ перевыпускают.

**Резервные копии базы** не настроены, решения о них в репозитории нет. Сервис и схему можно поднять заново
из `render.yaml` и миграций, данные игроков — нельзя.
