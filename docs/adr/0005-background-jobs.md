# 0005. Фоновые задачи: свой обработчик сейчас, Hangfire — для задач по расписанию

**Статус:** предложено, ждёт решения Никиты (issue #54). Сейчас в коде — свой обработчик (вариант А).

## Контекст

План (§2, §7, §8) называет Hangfire: «задачи Hangfire идемпотентны, время Минска», «пулы соединений: приложение 8, Hangfire 3»,
схема `hangfire` в Supabase; на показе (§11) открыт дашборд Hangfire (только чтение) — пункт 14 листика (§4) «Сложный
сервер: … фоновые задачи».

В коде Hangfire нет. Фоновая работа сделана одним `BackgroundService` — `CaptureWorker`:

- опрос раз в 5 секунд или по сигналу (новый кусок, заявка, завершение забега);
- по очереди: захваты → визиты → туман → откаты (движок участков однопоточный, ADR 0003);
- раз в час: журнал захватов старше 7 дней, сырые точки старше 14 дней, забытые забеги, удаление аккаунтов;
- идемпотентность — аренда заявок (`lease_until`, 2 минуты), отметки у забегов (`fog_stamped_at`, `visits_processed_at`,
  `points_purged_at`), блокировки PostgreSQL (`pg_advisory_xact_lock`: игрок — 1, туман игрока — 2, устройство — 3,
  тайлы — 100 + лига). Два экземпляра сервера во время деплоя друг другу не мешают.

Так получилось потому, что захваты должны обрабатываться за секунды после заявки, строго по одному и с сигналом «пора» —
это не «задача по расписанию», а очередь. Для неё Hangfire лишний: он опрашивает свою схему в той же бесплатной базе
(500 МБ, лимит соединений) и занимает память на Render Free (512 МБ).

## Решение (предлагаю)

**Гибрид.** Очередь захватов, визитов, тумана и откатов остаётся в своём обработчике. Задачи **по расписанию** — когда они
появятся — идут в Hangfire: ежедневный срез очков в 00:00 по Минску (§3.5), смена сезона (§3.4), итоги дуэлей (§3.14),
часовые чистки (перенести из `CaptureWorker`). Дашборд Hangfire — только чтение, для показа (§11).

До появления этих задач Hangfire не подключаем: сейчас ему нечего показывать.

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| **А. Только свой обработчик** (как сейчас) | Проще, меньше памяти и соединений, всё уже работает и покрыто тестами | На показе нет дашборда задач — придётся показывать логи и `/health/ready`; расписание «в 00:00 по Минску» писать самим |
| **Б. Всё в Hangfire**, включая захваты | Один механизм, дашборд со всем | Захват ждёт опроса очереди Hangfire вместо мгновенного сигнала; однопоточность движка придётся держать очередями Hangfire; переделка готового |
| **В. Гибрид** (предлагаю) | Быстрые захваты остаются; у расписания — надёжный планировщик с повторами и дашбордом для показа | Два механизма; таблицы Hangfire в той же бесплатной базе, 3 соединения из лимита Supabase |

## Последствия

- Для варианта В: пакет `Hangfire.PostgreSql`, схема `hangfire`, пул 3 соединения (как в плане), дашборд только для роли `admin`.
- Render Free засыпает без запросов — задачи по расписанию выполнятся при пробуждении; пингер (issue #39) держит сервер
  бодрствующим, так что опоздание — не больше интервала пингера.
- Если решим А — убрать Hangfire из PLAN.md (§2, §7, §8, §11) и придумать, что показать в пункте 14 вместо дашборда.
